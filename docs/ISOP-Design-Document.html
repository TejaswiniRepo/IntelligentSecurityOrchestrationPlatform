Overview

ISOP screens a user registration before the account is created: an LLM chooses which follow-up investigations to run, and a deterministic policy returns ALLOW, REVIEW or REJECT.

Problem. Conventional fraud orchestration runs a fixed sequence of checks for every request. Extending it means adding conditional logic for each new signal and relationship. ISOP tests whether an agent can pick follow-up checks from the evidence while access decisions stay rule-based and auditable.

Goals

  • Expose risk-signal checks as governed MCP tools with input validation and timeouts.
  • Let an LLM planner select follow-up tools from evidence, within an allowlist and a budget.
  • Keep the final decision in versioned, explainable policy code with reason codes.
  • Record a masked audit trace of every tool, signal, rule and decision.
  • Run fully offline on one laptop: local model, no cloud account, no internet.

Non-goals

  • The LLM never authorises, rejects or creates an account.
  • No real fraud vendors: all signals come from deterministic mock providers, labelled simulated.
  • No production deployment, authentication, rate limiting or account-recovery journey in this release.

Architecture

ISOP is one FastAPI process plus one MCP server subprocess and a local Ollama runtime; the planner advises, the policy decides.

The left column is the request path every registration takes. The orchestrator asks the planner which follow-up checks to run and calls tools through the MCP client; only the policy turns the collected signals into a decision, which is written to the audit trail and returned.

Each module has one responsibility and a typed boundary; only policy.py produces a decision.

MCP tools. Baseline: check_email_reputation, check_phone_risk, check_ip_risk, check_device_risk. Follow-up: check_device_history, get_registration_history (entity ip, phone or email).

Request flow

A registration check runs four baseline tools in parallel, then up to three planner turns, and only then asks the policy for a decision.

  1. The client posts the registration; FastAPI validates every field and drops the password.
  2. The orchestrator runs the four baseline MCP tools concurrently (phone only when supplied).
  3. Each planner turn sends the LLM sanitised evidence and the actions still available; the model returns steps and a done flag constrained by a JSON schema.
  4. The orchestrator validates each step (allowlist, entity, duplicates, budget), binds the argument values itself and calls the chosen follow-up tools.
  5. The loop ends when the planner is done, no actions remain, the budget of 4 follow-ups is used, or 3 turns have run. If Ollama fails, the rules planner takes that turn, labelled deterministic_fallback.
  6. The policy evaluates all signals; the orchestrator writes the masked audit trace and returns the decision, reason codes, planner_mode and trace.

Decision policy

Every rule is evaluated on every request and the most severe outcome wins (REJECT over REVIEW over ALLOW); thresholds live in config/policy.json, version reg-policy-2026.11.1.

RuleOutcomeFires when
R001_REQUIRED_SIGNAL_UNAVAILABLEReviewEMAIL, IP or DEVICE (and PHONE when supplied) did not return SUCCESS
R002_HARD_REJECT_INDICATORRejecta configured hard-reject reason code is present, e.g. DEVICE_LINKED_TO_MANY_ACCOUNTS
R003_MULTIPLE_HIGH_RISK_SIGNALSReject2 or more signals score 80 or higher
R004_SINGLE_HIGH_RISK_SIGNALReviewexactly 1 signal scores 80 or higher
R005_ELEVATED_RISK_SIGNALReviewany signal scores from 60 to 79
R006_COMPOSITE_RISK_CRITICALRejectweighted composite score is 70 or higher
R007_COMPOSITE_RISK_ELEVATEDReviewweighted composite score is 45 or higher
R008_REQUIRED_FOLLOW_UP_MISSINGReviewdevice 40+ without device history, or IP / phone 60+ without registration history for that entity
R000_NO_RISK_INDICATORSAllowno other rule fired

Composite weights: EMAIL 0.25, IP 0.25, DEVICE 0.25, PHONE 0.15, DEVICE_HISTORY 0.10, REGISTRATION_HISTORY 0.10, averaged over successful signals only.

i

Why R008 exists. It makes the policy, not the planner, own investigation completeness. A model that skips a needed check can cause a manual review, never an ALLOW on incomplete evidence. An inconsistent configuration (for example elevated threshold at or above high) stops the service at startup.

Known gaps: no API authentication or rate limiting, and device pseudonyms are unsalted SHA-256.

Resilience and offline operation

Every failure fails closed: a broken check or model can produce REVIEW or a labelled fallback, never a silent ALLOW.

FailureBehaviourVerified
Ollama not runningPlanner turn deterministic_fallback, status error; 30 s cooldown skips the model on later turnsLive: REJECT in 2.2 s, then LLM resumed after restart
Model not pulledSame fallback; error names the fix ollama pull qwen2.5:3b; no automatic downloadLive
Model timeout or malformed JSONSame fallback, error recordedUnit tests
LLM_FALLBACK=errorHTTP 503 with an explicit messageIntegration test
MCP tool missingSignal ERROR, R001 forces REVIEW; service still startsIntegration test
MCP tool slowSignal TIMEOUT after ISOP_TOOL_TIMEOUT_S (3 s), REVIEWIntegration test
Planner crashesInvestigation stops; policy decides on gathered evidenceIntegration test
✓

Offline guarantees. The runtime needs no Claude login, API key, Hugging Face token or internet. Ollama 0.40.10 runs CPU-only on 127.0.0.1 with qwen2.5:3b (1.9 GB). Swagger UI 5.34.0 is bundled. A socket guard in the test suite fails any connection to a non-loopback address. Only scripts/setup-online.ps1 touches the network.

Deployment and runbook

The target is one Windows 11 laptop (i5-12500H, 15.6 GB RAM, no NVIDIA GPU); setup needs internet once, the demo needs none.

One-time setup (online)

PowerShell
powershell -ExecutionPolicy Bypass -File scripts\setup-online.ps1

This creates .venv from requirements.txt, caches wheels in vendor\wheels, installs a CPU-only Ollama (35 MB downloaded instead of the 1.6 GB installer), verifies its Ollama Inc. signature, pulls qwen2.5:3b and runs the tests.

Demo day (offline)

  1. Free port 8000, plug in mains power, close heavy apps (the model needs about 3 GB free RAM).
  2. Terminal 1: powershell -ExecutionPolicy Bypass -File scripts\start-demo.ps1 starts Ollama on 127.0.0.1 if needed, never pulls, then serves the API on 127.0.0.1:8000.
  3. Terminal 2: powershell -ExecutionPolicy Bypass -File scripts\verify-demo.ps1 prints PASS/FAIL for API, MCP tools, policy, model, a warm-up inference and the ALLOW / REVIEW / REJECT cases.
  4. Browser: http://127.0.0.1:8000/docs, then submit examples/allow.json, review_tor_ip.json and reject_device_farm.json.

Fallback. start-demo.ps1 -Deterministic runs the full workflow with the rules planner, labelled deterministic.

Restore. .venv rebuilds offline from vendor\wheels (verified); Ollama and the model restore from a copy of %LOCALAPPDATA%\Programs\Ollama and %USERPROFILE%\.ollama\models.
